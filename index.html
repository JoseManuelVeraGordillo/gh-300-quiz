GUÍA DE ESTUDIO · GH-300

Guías de estudio GH-300

Resúmenes temáticos para reforzar conceptos, límites y buenas prácticas del examen.

La idea central

GitHub Copilot es un asistente de programación con IA integrado en el flujo de desarrollo. Puede proponer código, responder preguntas, explicar o refactorizar fragmentos y ayudar con pruebas y documentación. No conoce por completo tus requisitos ni sustituye el criterio del desarrollador: revisa cada resultado antes de incorporarlo.

01

Formas de trabajar

  • Sugerencias en el editor: aparecen como texto fantasma mientras escribes; acepta solo lo que te sirva.
  • Chat: permite preguntar, explorar código y pedir ayuda con tareas del proyecto.
  • Chat en línea: trabaja sobre el código seleccionado para explicar o proponer una edición concreta.
  • Los comentarios, el código abierto y la documentación aportan contexto a las sugerencias.
02

Capacidades y límites

  • Puede ayudar a: completar o generar código, explicar, refactorizar, proponer pruebas y revisar posibles mejoras.
  • No garantiza: que el código sea correcto, completo, seguro, eficiente o adecuado a la lógica de negocio.
  • Puede ignorar contexto importante, proponer patrones obsoletos o inseguros y rendir peor en tecnologías poco comunes.
  • Trátalo como asistente colaborativo, no como piloto automático ni sustituto de una revisión técnica.
03

Riesgos y uso responsable

Estudia los seis principios de IA responsable:

  • Equidad
  • Fiabilidad y seguridad
  • Privacidad y confianza
  • Inclusión
  • Transparencia
  • Responsabilidad

Ten presentes el sesgo, las vulnerabilidades, los secretos expuestos y las cuestiones de licencias o propiedad intelectual. La persona que integra el código sigue siendo responsable de revisarlo.

04

Validar antes de integrar

  • Revisa lógica, requisitos, seguridad, rendimiento y licencias; busca credenciales o secretos.
  • Ejecuta pruebas unitarias y de integración; define casos esperados antes de generar código cuando sea posible.
  • Aplica análisis estático y linters; considera fuzzing y escáneres de seguridad.
  • Observa registros y comportamiento en ejecución después del despliegue.
  • Usa control de versiones para revisar diferencias y volver a una versión anterior si es necesario.
05

Mejorar las sugerencias

  • Escribe instrucciones específicas e incluye objetivo, contexto, restricciones y ejemplos de estilo.
  • Refina el prompt de forma iterativa si la primera respuesta no cumple lo que necesitas.
  • Mantén el código y la documentación claros; los archivos enfocados facilitan aportar contexto relevante.
  • Revisa las dependencias externas y aplica las normas del proyecto y del equipo.
06

Instalación y solución de problemas

  • Instala VS Code y la extensión oficial de GitHub Copilot; inicia sesión con una cuenta que tenga acceso.
  • Si no conecta, comprueba Internet, proxy, red y posibles restricciones corporativas.
  • Si falla la autenticación, vuelve a iniciar sesión o renueva la autorización.
  • Si faltan archivos en el contexto, revisa exclusiones de Copilot, políticas y configuraciones del repositorio.
  • Actualiza VS Code y las extensiones, comprueba el acceso al plan y consulta los registros o límites de uso.

La interfaz y los pasos cambian entre versiones. Confirma los detalles en la documentación vigente de GitHub y VS Code.

Para responder preguntas

Recuerda la diferencia entre sugerir y garantizar: Copilot propone; el desarrollador verifica. Relaciona cada riesgo con una mitigación y memoriza los seis principios de IA responsable.

La idea central

La privacidad de Copilot depende de una combinación de plan, configuración personal, políticas de la organización y contexto compartido con el editor. Protege los datos sensibles antes de pedir ayuda y revisa las sugerencias: los filtros y las exclusiones reducen riesgos, pero no sustituyen la seguridad del repositorio ni el criterio humano.

01

Planes y tratamiento de datos

  • El material distingue planes individuales (Free, Pro y Pro+) y organizativos (Business y Enterprise); las funciones y controles varían entre planes.
  • En cuentas individuales, revisa los controles de sugerencias que coinciden con código público y las opciones de uso de datos para entrenamiento.
  • En organizaciones puede haber políticas y administración centralizadas sobre modelos, datos y acceso.
  • No infieras el uso o retención de datos solo por el nombre del plan: consulta los ajustes de tu cuenta, el contrato y la política vigentes.
02

Configuración e instrucciones

  • El editor puede permitir habilitar o deshabilitar Copilot en general o por lenguaje; una opción específica puede prevalecer sobre la general.
  • Los ajustes del usuario, del espacio de trabajo y las políticas de organización pueden tener distinto alcance o prioridad.
  • Las instrucciones del repositorio orientan el estilo y el contexto de las respuestas; no equivalen a una política de privacidad ni a una exclusión de contenido.
  • Comprueba el nombre y la ubicación de cada ajuste en la documentación de la versión que utilizas.
03

Exclusiones de contenido

  • Las exclusiones buscan impedir que rutas o archivos seleccionados se usen como contexto para sugerencias.
  • Úsalas para reducir la exposición de secretos, credenciales, datos personales y código confidencial; evita compartirlos directamente en prompts.
  • La configuración disponible y quién puede administrarla dependen del producto, el plan y las políticas de la organización.
  • Las referencias desde archivos permitidos, enlaces simbólicos, perfiles o contextos remotos pueden complicar el alcance: valida la configuración y sus límites.
04

Propiedad intelectual y contratos

  • Que una sugerencia sea generada por IA no elimina la obligación de comprobar licencias, derechos de terceros y normas aplicables.
  • Los filtros de coincidencia con código público pueden reducir ciertos riesgos; no garantizan que una sugerencia esté libre de reclamaciones.
  • Las garantías, indemnizaciones y responsabilidades dependen del plan, los términos aplicables y el uso de los controles requeridos.
  • Antes de aceptar una protección contractual como garantía, consulta el contrato vigente o al equipo legal.
05

Controles de seguridad

  • El filtro de coincidencias con código público trata coincidencias públicas; no debe confundirse con un análisis de duplicados del código privado de tu organización.
  • Copilot no reemplaza las herramientas de seguridad del repositorio. Complementa el flujo con revisión, pruebas y análisis estático.
  • Dependabot ayuda a gestionar dependencias vulnerables; code scanning busca vulnerabilidades en el código y secret scanning detecta secretos expuestos, según la configuración y el plan.
  • Configura permisos y políticas organizativas con el principio de menor privilegio.
06

Diagnóstico de exclusiones y sugerencias

  • Comprueba si Copilot está habilitado para el lenguaje y el ámbito correctos; revisa también las políticas y el acceso al plan.
  • Verifica exclusiones en el perfil, el espacio de trabajo o el contexto remoto donde realmente trabajas; revisa errores y registros.
  • Tras cambiar ajustes, actualiza o reinicia el editor y las extensiones si la documentación lo recomienda.
  • Si una sugerencia parece insegura, incorrecta o basada en contenido excluido, no la aceptes: conserva el contexto necesario para investigar sin exponer datos sensibles.

Para responder preguntas

Distingue el filtro de código público de las exclusiones de contenido; separa instrucciones del editor de controles de privacidad; y recuerda que Copilot no detecta duplicados internos ni ofrece garantías legales automáticas.

Planes, políticas de datos, nombres de ajustes y mecanismos de exclusión cambian con el tiempo. Contrasta los detalles concretos con la documentación y los términos actuales de GitHub Copilot.

La idea central

GitHub Copilot puede acelerar la creación y mejora de pruebas, desde el esqueleto inicial hasta los casos límite y las aserciones. La cobertura generada no garantiza que una prueba sea correcta ni que compruebe el comportamiento esperado: revisa el diseño, ejecuta la suite y valida que falle cuando el código falla.

01

Suites y tipos de prueba

  • Pide pruebas unitarias para unidades aisladas e integración para comprobar cómo colaboran varios componentes.
  • Según el proyecto, también puedes trabajar con pruebas de componentes y end-to-end; usa frameworks estándar del stack.
  • Da contexto sobre el comportamiento esperado, las herramientas existentes y los comandos del proyecto antes de pedir cambios.
  • Revisa dependencias, configuración y comandos que Copilot proponga instalar o ejecutar.
02

Casos límite

  • Solicita escenarios de límites, entradas vacías o inválidas, espacios, valores extremos, errores y combinaciones inusuales.
  • Contrasta cada caso con los requisitos: más pruebas no siempre significa mejor cobertura.
  • Comprueba que los casos detecten defectos reales y que no dependan de detalles internos innecesarios.
03

Boilerplate y estructura

  • Copilot puede proponer configuración del framework, archivos de prueba, datos de prueba, mocks y scripts.
  • Revisa y acepta cambios de forma consciente; ejecuta los comandos y comprueba que las pruebas realmente corran.
  • Adapta el esqueleto al proyecto en vez de añadir herramientas o dependencias sin necesidad.
04

Aserciones precisas

  • Una aserción debe expresar un resultado observable que se desprenda del requisito: salida, estado, error o interacción.
  • Usa Arrange, Act, Assert para preparar el escenario, ejecutar la acción y verificar el resultado.
  • Incluye resultados positivos y negativos cuando proceda; evita pruebas que siempre pasan o que solo repiten la implementación.
  • Mocks y stubs aíslan dependencias, pero verifica que no oculten el comportamiento que querías probar.
05

Patrones y calidad

  • Conoce la pirámide de pruebas: unitarias, integración y end-to-end; el equilibrio depende del sistema.
  • Otros enfoques incluyen pruebas de componentes, regresión, rendimiento, seguridad y accesibilidad.
  • Patrones de automatización comunes: Arrange-Act-Assert, mocks/stubs y Page Object Model para interfaces web.
  • Pide a Copilot que explique o revise pruebas existentes, y comprueba legibilidad, mantenimiento y falsos positivos.
06

Revisión colaborativa

  • Las instrucciones compartidas del proyecto pueden ayudar a mantener convenciones de nombres, estructura y herramientas de prueba.
  • La revisión por pares detecta huecos, aserciones débiles y supuestos que el autor o la IA pasaron por alto.
  • Copilot puede explicar, refactorizar y documentar tests; el equipo sigue siendo responsable de los estándares y la aprobación.
07

Pruebas de seguridad

  • Pide revisar riesgos como inyección SQL, XSS, credenciales expuestas y uso de APIs inseguras; valida las propuestas con análisis y pruebas.
  • Las consultas parametrizadas separan datos de la estructura SQL; al insertar texto no confiable en el DOM, evita tratarlo como HTML ejecutable.
  • Code scanning, Dependabot y secret scanning complementan las pruebas; Copilot no reemplaza estas herramientas ni una revisión de seguridad.
08

Rendimiento y testabilidad

  • Pide identificar posibles cuellos de botella, pero mide antes y después con datos representativos.
  • El ejemplo del curso contrasta búsquedas repetidas con indexOf (O(n²)) con un Set (O(n) promedio) para eliminar duplicados.
  • Funciones pequeñas y dependencias inyectables facilitan pruebas aisladas; la testabilidad puede ayudar al diseño, pero no garantiza por sí sola mejor rendimiento.
  • Comprueba que una optimización conserve el comportamiento mediante pruebas de regresión.

Para responder preguntas

Copilot ayuda a generar suites, boilerplate, aserciones y casos límite. El desarrollador debe revisar la intención, ejecutar las pruebas y verificar seguridad y rendimiento; las sugerencias no sustituyen la validación.

La idea central

Elige el plan según el uso individual o la necesidad de administrar Copilot en una organización. Free, Pro y Pro+ se orientan a desarrolladores individuales; Business añade administración y políticas de equipo; Enterprise amplía los controles y el contexto organizativo. Las funciones y los límites cambian con el tiempo.

01

Planes individuales

  • Free: permite probar Copilot o usarlo ocasionalmente, con límites de uso incluidos.
  • Pro: para desarrolladores que lo usan con frecuencia y necesitan más capacidad, modelos y solicitudes premium.
  • Pro+: para uso intensivo que requiere una cuota mayor de solicitudes premium y acceso ampliado a modelos.
  • El curso cita como referencia 2.000 completaciones y 50 solicitudes de chat mensuales para Free, 300 solicitudes premium para Pro y 1.500 para Pro+. Verifica las cuotas actuales antes de tomar una decisión.
02

Business para equipos

  • Está diseñado para organizaciones que necesitan gestionar licencias y acceso de forma centralizada.
  • Permite administrar políticas organizativas y establecer controles compartidos para los equipos.
  • El material del curso también destaca la indemnización de propiedad intelectual, las exclusiones de contenido y los registros de auditoría, sujetos al plan y a los términos aplicables.
03

Enterprise para organizaciones grandes

  • Se orienta a organizaciones que necesitan administración a escala empresarial, controles adicionales y opciones avanzadas de personalización.
  • El curso resalta la gestión jerárquica de políticas y acceso, y los informes de uso y auditoría.
  • La integración con repositorios y conocimiento interno puede aportar contexto organizativo a Copilot, según las funciones disponibles en el plan vigente.
04

Exclusiones y auditoría

  • Las exclusiones de contenido permiten indicar rutas que Copilot no debe usar como contexto, por ejemplo archivos sensibles.
  • Configúralas en el ámbito correcto (usuario, organización o repositorio, según corresponda) y verifica su efecto; no compartas secretos en prompts.
  • Los registros de auditoría ayudan a revisar actividad y apoyar necesidades de cumplimiento; el curso muestra su exportación a CSV o JSON.
  • Las API de administración pueden automatizar tareas, pero sus permisos y disponibilidad dependen del plan; el curso advierte que algunas operaciones mostradas eran experimentales.
05

Bases de conocimiento

  • Una base de conocimiento organiza repositorios para ofrecer a Copilot contexto reutilizable sobre el código y las convenciones internas.
  • El flujo del curso crea la base desde la configuración de Copilot de la organización, añade repositorios y espera a que se indexen.
  • Comprueba qué planes, repositorios y opciones de indexación admite actualmente tu organización antes de diseñar una implementación.
06

Cómo elegir

  • Uso ocasional o evaluación: compara primero las cuotas de Free.
  • Desarrollo individual frecuente: valora Pro; para un uso premium intensivo, compara Pro+.
  • Equipo que requiere licencias y políticas centralizadas: evalúa Business.
  • Organización con gobernanza amplia y contexto de repositorios internos: evalúa Enterprise.
  • Considera también las políticas de datos, seguridad, cumplimiento, soporte y coste total.

Para responder preguntas

Asocia Free, Pro y Pro+ con el uso individual y sus distintos niveles de capacidad; Business con la administración de equipos; y Enterprise con controles y contexto organizativo avanzados. No confundas una cuota citada en el curso con un límite vigente.

La idea central

Copilot Chat permite resolver dudas, crear o revisar código y recibir orientación contextual dentro del entorno de desarrollo. Copilot CLI lleva la asistencia al terminal. En ambos casos, aporta contexto claro, revisa lo que propone y valida los cambios antes de integrarlos o ejecutar comandos.

01

Casos de uso de Chat (Chat use cases)

  • Iniciar proyectos (project scaffolding): pedir una estructura inicial y archivos de configuración para el stack elegido.
  • Crear y completar archivos (file creation and population): especificar formato, campos, ejemplos y restricciones, y revisar el resultado antes de aplicarlo.
  • Obtener orientación de implementación (implementation guidance): consultar cómo implementar una tarea, qué herramientas usar y qué pasos validar.
  • Puede generar datos de muestra (sample data), por ejemplo un archivo JSON, y ayudar a configurar un servidor simulado (mock server).
  • El contexto de los archivos abiertos o seleccionados ayuda a adaptar la respuesta al proyecto.
02

Instrucciones del repositorio (repository instructions) y calidad de respuesta

  • El archivo de instrucciones de Copilot (Copilot instructions file), .github/copilot-instructions.md, puede comunicar convenciones compartidas del repositorio, como estilo, pruebas, documentación y manejo de errores.
  • Especifica objetivo, contexto, restricciones y casos límite; refina el prompt si la respuesta es incompleta.
  • Copilot puede omitir validaciones o escenarios no solicitados explícitamente. Pide que considere entradas inválidas y otros casos límite cuando corresponda.
  • Las instrucciones orientan la generación, pero no garantizan que la salida cumpla los requisitos.
03

Revisión de código (code review) y feedback

  • Selecciona el código pertinente (code selection) y pide una revisión para detectar defectos, problemas de legibilidad o diferencias con las convenciones del proyecto.
  • Evalúa cada sugerencia por separado: aplica las útiles y descarta las que no representan la intención del equipo.
  • Revisa especialmente cambios funcionales y de seguridad; ejecuta pruebas y herramientas del proyecto antes de integrar.
  • El feedback efectivo consiste en indicar qué falta o qué no encaja y aportar el contexto necesario para una nueva iteración.
04

Comandos de barra (slash commands)

  • /explain pide explicar el código o la selección.
  • /fix solicita analizar y proponer una corrección.
  • /tests ayuda a generar pruebas; /doc propone documentación.
  • /edit y /generate ayudan a modificar o crear código, según el contexto.
  • Escribe / en el chat para ver los comandos disponibles en tu versión; las opciones dependen de la superficie y del producto.
05

Copilot CLI (command-line interface)

  • La CLI permite solicitar ayuda desde el terminal para tareas relacionadas con el desarrollo y GitHub, sin cambiar de aplicación.
  • El curso muestra la autenticación con GitHub CLI y una extensión de Copilot; ese flujo puede haber cambiado. Sigue la guía oficial vigente para instalar y autenticar la CLI disponible en tu entorno.
  • Antes de ejecutar una propuesta, inspecciona el comando, la carpeta de trabajo, los permisos y sus posibles efectos; confirma cualquier operación que modifique o elimine datos.
  • No incluyas tokens, contraseñas ni otros secretos en prompts o comandos compartidos.

Para responder preguntas

Chat sirve para crear, explicar, editar y revisar con contexto; las instrucciones del repositorio ayudan a mantener convenciones; los comandos de barra agilizan tareas comunes; y la CLI acerca la asistencia al terminal. En todos los casos, el desarrollador revisa, prueba y decide.

Los nombres y la disponibilidad de comandos, extensiones y métodos de instalación pueden variar entre versiones. Consulta la documentación oficial actual antes de configurar Copilot CLI.

La idea central

Copilot combina la solicitud con contexto de desarrollo para generar una respuesta. Para estudiar el flujo, recuerda: el IDE recopila contexto, se construye el prompt, un proxy aplica filtros, el modelo genera una respuesta y se revisa antes de mostrarla. El tratamiento real de datos depende del producto, plan, configuración y políticas vigentes.

01

Tipos de datos (data types)

  • Datos de interacción (engagement data): actividad de uso y señales sobre sugerencias aceptadas o rechazadas, según la configuración aplicable.
  • Prompts (prompts): consultas que envías y el contexto que las acompaña, que puede incluir fragmentos o nombres del código.
  • Sugerencias (suggestions): código o explicaciones generadas por Copilot en respuesta.
  • Feedback (feedback): reacciones y comentarios que el usuario decide enviar sobre las respuestas.
02

Completado de código y chat (code completion vs. chat)

  • En el completado, la extensión del IDE usa el archivo y el entorno de edición para inferir qué código podría venir a continuación.
  • En Chat, el prompt suele ser una pregunta o instrucción explícita y puede incluir referencias o contexto adicional.
  • Ambos flujos pueden incorporar contexto, pasar por servicios de procesamiento y devolver una sugerencia al entorno de desarrollo.
  • Cada interacción puede consumir cuota según el plan y el producto; revisa los límites actuales de tu cuenta.
03

Fuentes de contexto (context sources)

  • Archivo actual (current file), código resaltado (selected code) y otros archivos abiertos o relacionados.
  • Estructura del espacio de trabajo (workspace), referencias del repositorio y el historial pertinente de la conversación.
  • Según las funciones disponibles, puedes adjuntar contexto mediante referencias como @ o #, instrucciones del repositorio o fuentes conectadas.
  • Aporta solo contexto necesario y autorizado; no incluyas secretos ni información sensible sin aprobación.
04

Construcción del prompt (prompt construction)

  • El sistema combina la petición con información contextual y la organiza para el modelo.
  • La solicitud puede pasar por filtros de contenido y controles de seguridad antes de llegar al modelo de lenguaje grande (large language model, LLM).
  • Escribir una petición específica y elegir contexto relevante reduce ambigüedad y ruido.
  • Los detalles de infraestructura, filtros y políticas pueden variar; estudia el diagrama del curso como modelo conceptual, no como contrato técnico inmutable.
05

Ciclo de vida de una sugerencia (suggestion lifecycle)

  1. El IDE aporta contexto (IDE provides context).
  2. Se construye el prompt (prompt is constructed).
  3. El proxy filtra o sanitiza el prompt (proxy filters the prompt).
  4. El LLM formula una sugerencia (LLM generates a suggestion).
  5. La respuesta pasa por controles de seguridad y calidad (response is checked).
  6. La sugerencia se presenta en el IDE (suggestion appears in the IDE).
06

Cómo genera texto el modelo (response generation)

  • Tokenización (tokenization): divide la entrada en unidades que el modelo puede procesar; no siempre coinciden con palabras completas.
  • Incrustaciones (embeddings): representan tokens como valores numéricos que capturan relaciones aprendidas.
  • Predicción probabilística (probabilistic prediction): el modelo estima qué token puede seguir según la entrada y el contexto.
  • La respuesta se genera progresivamente; el resultado es una predicción del modelo, no una garantía de exactitud.

Para responder preguntas

Distingue prompt (entrada) de sugerencia (respuesta); identifica como contexto el archivo actual, el código seleccionado y el espacio de trabajo; y memoriza la secuencia IDE → prompt → proxy → LLM → revisión de respuesta → IDE.

Las afirmaciones del curso sobre retención, ubicación de datos, modelos, filtros y subprocesadores pueden quedar desactualizadas. Para decisiones de privacidad, consulta la documentación, configuración y términos actuales del plan.

La idea central

La ingeniería de prompts (prompt engineering) consiste en expresar con claridad qué necesitas y aportar el contexto adecuado para orientar a Copilot. Un buen prompt reduce ambigüedad, pero la respuesta sigue necesitando revisión y validación.

01

Componentes de un buen prompt (prompt components)

  • Objetivo (purpose): indica la tarea y el resultado esperado de forma directa.
  • Contexto (context): menciona lenguaje, framework, archivos pertinentes, comportamiento existente y restricciones del proyecto.
  • Ejemplos (examples): muestra formato, estilo, entradas o salidas cuando necesites una respuesta con un patrón concreto.
  • También puedes especificar formato de respuesta, audiencia, tono, compatibilidad y criterios de aceptación.
02

Zero-shot, one-shot y few-shot

  • Zero-shot: pedir una tarea sin incluir ejemplos; es útil para preguntas directas y tareas comunes.
  • One-shot: incluir un ejemplo para señalar el formato o patrón deseado.
  • Few-shot: proporcionar varios ejemplos para orientar estilo, estructura o convenciones específicas.
  • Elige según cuánto necesite Copilot inferir: los ejemplos añaden orientación, pero no garantizan que la respuesta sea correcta.
03

Contexto e historial de chat (chat history)

  • Mantén abiertos o selecciona los archivos relevantes y evita incluir contexto ajeno a la tarea.
  • El historial puede ayudar a continuar una conversación y referirse a decisiones anteriores dentro del contexto disponible.
  • Si cambias de tarea, inicia una conversación nueva cuando convenga; no des por sentado que esto borra datos retenidos o elimina todo contexto del proyecto.
  • La disponibilidad y persistencia del historial dependen del producto, la configuración y las políticas actuales.
04

Buenas prácticas (best practices)

  • Empieza con el objetivo general y añade requisitos concretos, restricciones y casos límite.
  • Divide las tareas grandes en pasos pequeños y verificables; evita referencias ambiguas como “esto” si no está claro a qué apuntan.
  • Refina el prompt según lo que faltó en la respuesta y comprueba cada cambio con pruebas o revisión.
  • Usa ejemplos y convenciones del proyecto para guiar el resultado; aporta solo contexto pertinente y autorizado.
  • Un prompt claro reduce iteraciones innecesarias, pero no sustituye el criterio del desarrollador.
05

Lenguaje y entorno (language and environment)

  • Indica el lenguaje de programación, framework, plataforma o versión si no resulta evidente por el código y el contexto.
  • Para web, aclara si trabajas en frontend o backend y qué entorno usas, por ejemplo Node.js o ASP.NET.
  • Para bases de datos, describe el resultado o los datos que necesitas; para lenguajes de bajo nivel, especifica restricciones de memoria y rendimiento.
  • Puedes pedir la respuesta en un idioma humano concreto y ajustar opciones por lenguaje en el IDE cuando estén disponibles.
06

Flujo de trabajo de un prompt (prompt workflow)

  1. Define el objetivo, el alcance y el resultado esperado.
  2. Aporta contexto, ejemplos y restricciones relevantes.
  3. Permite que Copilot interprete la solicitud y use el contexto y las herramientas disponibles.
  4. Revisa la respuesta; aclara o refina el prompt si falta información.
  5. Valida el resultado con pruebas, herramientas y criterios del proyecto antes de integrarlo.

Para responder preguntas

Recuerda la tríada objetivo + contexto + ejemplos. Zero-shot no incluye ejemplos; one-shot incluye uno; few-shot incluye varios. El historial ayuda a mantener contexto, y la iteración permite corregir respuestas incompletas.

Las opciones de idioma, contexto, historial y personalización dependen de la versión del IDE, el producto, el plan y las políticas aplicables.

La idea central

Copilot puede apoyar tareas en distintas fases del desarrollo: aprender tecnologías, traducir y modernizar código, documentar proyectos, generar datos de prueba y depurar. Su mayor utilidad está en acelerar un primer borrador o análisis; el desarrollador conserva la responsabilidad de revisar, probar y validar el resultado.

01

Aprender lenguajes y frameworks (learning languages and frameworks)

  • Pide ejemplos pequeños, explicaciones de sintaxis y una estructura inicial para una tecnología nueva.
  • Solicita aclaraciones sobre patrones del lenguaje, por ejemplo el punto de entrada if __name__ == "__main__": en Python.
  • Indica tu nivel, entorno y objetivo de aprendizaje; ejecuta el ejemplo y compáralo con la documentación vigente.
02

Traducir código (code translation)

  • Especifica el lenguaje de origen y el destino, archivos pertinentes y comportamiento que debe conservarse.
  • Para una conversión JavaScript a TypeScript, por ejemplo, considera tipos, dependencias, configuración y compilación.
  • La traducción inicial puede dejar errores de tipos o lógica: compila, ejecuta pruebas y revisa la equivalencia funcional.
03

Reducir cambios de contexto (context switching)

  • Chat en el IDE puede explicar archivos, ayudar con varias tecnologías y relacionar módulos sin salir del entorno de trabajo.
  • El archivo activo, la selección y el espacio de trabajo ayudan a contextualizar las solicitudes; adjunta referencias relevantes cuando haga falta.
  • No supongas que Copilot ve automáticamente todos los archivos o conoce decisiones no documentadas.
04

Documentar proyectos y código (project and code documentation)

  • Pide documentación de proyecto como un README, explicando propósito, instalación, configuración, uso y pruebas.
  • Solicita comentarios para archivos, funciones, procesos o APIs; especifica audiencia y nivel de detalle.
  • Comprueba que la documentación coincida con el comportamiento real, los comandos y la estructura del proyecto.
05

Datos de muestra y servidores simulados (sample data and mock servers)

  • Solicita conjuntos de datos realistas con campos, cantidades, formatos y restricciones concretas.
  • Copilot puede ayudar a crear archivos JSON y proponer cómo servirlos con un servidor simulado (mock server).
  • Usa datos ficticios, nunca datos personales o credenciales reales; valida el formato, los casos límite y la configuración antes de usarla.
06

Modernizar aplicaciones heredadas (legacy modernization)

  • Pide analizar una función y proponer refactorizaciones o sintaxis moderna en pasos pequeños.
  • Indica restricciones de compatibilidad y el comportamiento que debe mantenerse; revisa dependencias y efectos secundarios.
  • Compara resultados antes y después y ejecuta pruebas de regresión para comprobar que la modernización conserva la funcionalidad.
07

Depuración (debugging)

  • Comparte el error, el resultado esperado y el observado, el contexto relevante y los pasos para reproducirlo.
  • Expresa las restricciones que deben preservarse, como mantener una función o un comportamiento existente.
  • Evalúa la causa propuesta, aplica cambios de forma controlada y verifica el arreglo con pruebas o reproduciendo el escenario.
08

Copilot a lo largo del SDLC (software development lifecycle)

  • Planificación y diseño: explorar ideas, prototipos, estructuras y esquemas.
  • Desarrollo y pruebas: completar o generar código, traducir, refactorizar y proponer pruebas.
  • Documentación y mantenimiento: explicar sistemas, actualizar documentación y analizar posibles mejoras o errores.
  • En todas las fases, verifica la exactitud, seguridad, licencias, rendimiento y cumplimiento con las necesidades del proyecto.

Para responder preguntas

Relaciona cada escenario con su uso: ejemplos para aprender, contexto para trabajar entre lenguajes, instrucciones para traducir sin perder funcionalidad, README y comentarios para documentar, datos ficticios para pruebas, cambios graduales para modernizar y reproducción más pruebas para depurar.

Copilot puede proponer código, documentación, datos y soluciones, pero no garantiza que sean correctos, seguros o completos. Revisa cada resultado y valida las afirmaciones con el proyecto y sus pruebas.
